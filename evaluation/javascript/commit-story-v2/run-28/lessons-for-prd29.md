## Post-Write-Up Correction

- **Fix-verification-by-log-grep missed a live SCH-003 recurrence.** The first pass of `run-summary.md` checked `spiny-orb-output.log`'s prose for `String(` and found nothing suspicious, and reported RUN27-3 as "no recurrence observed." A CodeRabbit CLI review of the PRD branch caught the actual discrepancy: `summarize.js`'s committed source sets `months_generated_count`/`months_failed_count` (both `type: int`) via `String(result.generated.length)`/`String(result.failed.length)` — present in both the debug dump and the instrument branch's committed file, just never spelled out in the log's narrative sections. **Recommend for PRD #29's template**: fix-verification for both rules must read the actual committed or debug-dumped source directly, not just the log's Schema Extensions/Agent Notes sections (those describe *new* extensions and reasoning, not necessarily every `setAttribute` call on an *existing* key). This applies to SCH-003 (check every numeric-typed key's call sites for a `String()`/type mismatch) and equally to SCH-002 (check every previously-registered key — numeric or not — for a semantic mismatch or reuse-across-concepts, as with `dates_requested`'s week/month reuse and `is_merge`/`parent_count`'s inconsistent duplicate-key handling this run).
- **A local CodeRabbit review on the eval-artifact branch caught a real evaluation-quality bug, not just a style nit.** Worth normalizing as a standard second pass on any run-summary/findings write-up before reporting to Whitney, not just before opening a PR — this run's write-up was corrected before it caused a wrong recommendation to the spiny-orb team.
- **The log-only-check gap recurred a second time on a different file** (`summary-detector.js`), and again after per-file evaluation, not before it — confirming this isn't a one-off miss but a systematic blind spot. The eventual fix wasn't "read more carefully" — it was per-file evaluation's own methodology (direct `git show` + line-by-line registry comparison for every `setAttribute` call) catching what a targeted grep couldn't. **Recommend for PRD #29**: don't treat run-summary.md's fix-verification and per-file evaluation as sequential/redundant steps — per-file evaluation is the actual verification method for SCH-002/SCH-003; run-summary.md's early pass should be labeled provisional until per-file evaluation confirms or corrects it, not treated as a completed finding in its own right.
- **Delegated per-file evaluation subagents had no Datadog MCP access in any of ~14 background agent runs this session**, while the coordinating session did. This meant the D-2 trace-supplement step (cross-checking findings against live traces) was silently skipped by every subagent and had to be redone as a separate follow-up pass by the coordinating session after the fact. **Recommend for PRD #29's D-2 protocol**: state explicitly that trace supplementation is the coordinating session's responsibility, not something to expect from delegated subagents, and schedule it as its own pass after per-file evaluation completes rather than assuming it happens inline.
- **A real person's name appeared unredacted in this run's own working documents** while confirming a PII-exposure finding live via Datadog — the same category of exposure the finding itself was about. Caught by a CodeRabbit review, not by the person writing it. **Recommend for PRD #29's D-2 protocol**: any live-trace value pulled in as evidence for a PII/CDQ-007 finding must be redacted (e.g. `<redacted-person-name>`) in the same edit that adds it to a document, not as a follow-up cleanup step.
- **A file list (RUN27-4's "original 7 affected files") got silently corrupted across multiple retypings within the same run's documents.** The correct list (from run-27's own rubric-scores.md) is `claude-collector.js, context-integrator.js, journal-paths.js, summarize.js, summary-detector.js, auto-summarize.js, summary-manager.js` — but `run-summary.md` and `rubric-scores.md` each independently retyped a *different*, wrong 7-file list (one included `journal-manager.js`/`index.js`, neither of which was ever part of the original finding) before being caught and corrected. **Recommend for PRD #29**: when a canonical list needs to appear in multiple documents, copy it verbatim from its source of truth (the prior run's own rubric-scores.md) rather than reconstructing it from memory each time — reconstruction is where the corruption happened, repeatedly, in this run.
- **A validator's severity classification for the identical attribute and code pattern changed between runs with no visible code change to explain it** — `git-collector.js`'s `commit_story.commit.author` PII was a blocking canonical failure in run-27 and a non-blocking advisory in run-28. This is worth its own investigation thread in the handoff, separate from "the agent regressed a fix" — it may indicate the validator itself is non-deterministic or was silently changed.
- **"Resolved" needs a stated scope every time it's used for a multi-file fix.** This run's CDQ-007/RUN27-4 status went through several correction cycles because early drafts said "RESOLVED" when the accurate claim was "resolved at 6 of 7 files." **Recommend for PRD #29's template**: for any fix that was originally reported across N files, always state the fixed/total ratio explicitly (e.g. "6 of 7") rather than a bare PASS/FAIL or RESOLVED/UNRESOLVED, even when the majority is fixed.
- **D-15's targeted `find -delete` restore step may still be broader than necessary.** A second CodeRabbit CLI review of the PRD branch (2026-09-18, after the baseline-comparison and its own follow-up fix commits) flagged the IS scoring milestone's restore sequence (`find src/ examples/ -name '*.instrumentation.md' -delete`) as still deleting by filename pattern rather than by the exact set of paths the instrument-branch checkout actually added. D-15 already considered and rejected the broader `git clean -fd` alternative for the same reason (it could delete unrelated untracked work), but didn't consider capturing the exact added paths from the index before the `git reset` step as a third, more precise option. Flagged as real but deferred — the current approach is a deliberate, documented tradeoff (D-15), not an oversight, and no run in the series has actually lost an unintended file to it. **Recommend for PRD #29's template**: if this restore step is revisited, prefer capturing the exact paths (e.g. `git diff --name-only --diff-filter=A main <instrument-branch> -- src/ examples/`) before the `git reset`, then deleting only those captured paths, over a suffix-based `find`.
- **CDQ-006's COV-001-entry-point exemption is applied inconsistently across per-file evaluation sections, and the rule's own scope has never been written down.** Run-27's `rubric-scores.md` narrated, as an observed agent-reasoning pattern rather than a stated rule, that "COV-001 entry-point spans are exempt from the guard requirement." Run-28's `per-file-sections/08-journal-manager.md` invoked that same exemption to pass CDQ-006 outright for both of its spans (mixed guarded/unguarded `setAttribute` calls, no expensive computation involved). `per-file-sections/09-summary-manager.md` correctly failed CDQ-006 for its file but flagged the *absence* of COV-001 entry-point status as part of why — implying entry-point status would have changed the verdict there too, which was never tested since `rubric-scores.md`'s final FAIL reasoning for `summary-manager.js` doesn't actually depend on entry-point status (it cites "no stated exemption basis" instead). Caught by a CodeRabbit CLI review of the PRD branch, 2026-09-18 — flagged as real but deferred rather than fixed inline, since resolving it means re-litigating an already-reconciled, already-scored CDQ dimension that fed into the reported 21/25. **Recommend for PRD #29's template**: before per-file evaluation starts, write down explicitly whether CDQ-006's isRecording-guard requirement is exempt for COV-001 entry-point spans regardless of computation cost, or only exempt for genuinely cheap computations (`.length`/`.size` property access) regardless of entry-point status — pick one, and apply it uniformly across all per-file sections in the same run.
