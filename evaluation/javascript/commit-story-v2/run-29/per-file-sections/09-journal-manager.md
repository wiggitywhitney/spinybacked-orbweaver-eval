**Unrubriced findings**:
- **New throw path from `toISOString()` (rule-fit item 9).** Three call sites can throw `RangeError: Invalid time value` on an Invalid Date. The `!= null` guards stop null and undefined but not an Invalid Date.
  - Line 185 in `saveJournalEntry`: `new Date(commit.timestamp).toISOString()`. In the original, an Invalid Date `commit.timestamp` did not throw. `getJournalEntryPath` built a `NaN-NaN` path through `getFullYear()`/`getDate()`, and `formatTimestamp` returned "Invalid Date", so the entry was still written. Instrumented, the span catch records the error and rethrows it, so no entry is written. Because the site sits inside `if (span.isRecording())`, it throws only when the span is sampled.
  - Lines 376 and 379 in `discoverReflections`: `new Date(startTime).toISOString()` and `new Date(endTime).toISOString()`. In the original, an Invalid Date window made `getYearMonth` return `NaN-NaN`, `getYearMonthRange` returned `[]`, and the function returned `[]`. Instrumented, the `RangeError` propagates to the caller in `index.js` (line 587). These two sites have no `isRecording()` guard, so they throw even when the span is not sampled.
  - Both inputs come from `new Date(<git output string>)`: `git-collector.js` line 80 (`timestamp: new Date(timestampStr)`, where `timestampStr` is `lines[bodyEndIndex + 3]` and can be undefined) and `getPreviousCommitTime` in `index.js` (`new Date(output.trim())`). The exposure is narrow but real. The agent's thinking acknowledged it: "accepting that an invalid timestamp could still throw".
- **`commit_story.journal.entry_date` can name the wrong day (correct type, right registered key, wrong value).** Line 185 takes the date from `toISOString()`, which is UTC. The journal file the entry is written to is named by `getDateString` in `journal-paths.js` (line 32), which uses local `getFullYear()/getMonth()/getDate()`. For a commit made late in the evening west of UTC, for example 8 PM CDT, `entry_date` reports the next day while the entry lands in the current day's file. This is not a SCH-002 FAIL, because the key is the right noun for the value's concept. It is a data-quality defect that no rule checks.
