Fixed by bumping the baseline to major 7 (taze PR #12, merged) — but also found a latent fragility CodeRabbit caught: the `'default'`-mode undefined-case assertion used an exact-pin literal (`'7.0.0'`/formerly `'6.0.0'`) that could itself become a real published version, silently breaking the same way again. This class of test (asserting against live third-party registry data) will keep drifting on a schedule tied to the real package's release cadence, not to anything in this repo — worth a standing watch item for any eval target whose test suite hits a live external API.

## Generalizable Process Improvements

- **When writing PR artifact evaluation's schema-accuracy table, quote per-file evaluation's exact attribute/file pairings rather than summarizing from memory — cross-file attribute names are easy to conflate when two files handle structurally similar operations.** CodeRabbit CLI caught `pr-artifact-evaluation.md` attributing `taze.io.catalogs_count` to both `pnpmWorkspaces.ts` and `yarnWorkspaces.ts`, when the attribute is exclusive to `yarnWorkspaces.ts` — `pnpmWorkspaces.ts`'s equivalent count attribute is actually `taze.check.packages_loaded` (a different name, from the disguised-schema-laundering SCH-003 pattern, not the literal-mismatch one). Both files handle a "count of catalogs/workspaces" concept, which made the mix-up easy to write and easy to miss on self-review. Fix: when compiling the schema-accuracy table, copy the exact attribute name and file from each file's own per-file evaluation section rather than reconstructing the pairing from the narrative summary.
- **A milestone step that commits a fix directly to a target fork's `main` needs an explicit branch-and-PR reminder.** Mid pre-run-verification, a test fix got committed directly to taze's `main` before catching that this violates the global "feature branches only" rule — even for a solo-owned eval-target fork with no other contributors. Recovered by branching off the bad commit, hard-resetting `main` to `origin/main`, then pushing/PR'ing/CodeRabbit-reviewing/merging normally. Future template text for "target repo readiness" pre-run steps should say explicitly: any fix needed to make the target's own test suite pass goes through a branch + PR, never a direct commit to main, regardless of how trivial the fix or how solely-owned the fork is.
