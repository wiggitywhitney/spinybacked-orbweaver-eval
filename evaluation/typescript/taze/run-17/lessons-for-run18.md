Fixed by bumping the baseline to major 7 (taze PR #12, merged) — but also found a latent fragility CodeRabbit caught: the `'default'`-mode undefined-case assertion used an exact-pin literal (`'7.0.0'`/formerly `'6.0.0'`) that could itself become a real published version, silently breaking the same way again. Replaced with `'999.0.0'`, a version number that is not tied to any live major-version boundary and effectively never going to be published by TypeScript, decoupling that specific assertion from real release cadence. Not a hard guarantee — a truly stable assertion would use a mocked registry fixture instead of live data — but it removes the specific drift mechanism that broke `6.0.0` and `7.0.0` before it. This class of test (asserting against live third-party registry data) will keep drifting on a schedule tied to the real package's release cadence, not to anything in this repo — worth a standing watch item for any eval target whose test suite hits a live external API.

## Generalizable Process Improvements

- **A milestone step that commits a fix directly to a target fork's `main` needs an explicit branch-and-PR reminder.** Mid pre-run-verification, a test fix got committed directly to taze's `main` before catching that this violates the global "feature branches only" rule — even for a solo-owned eval-target fork with no other contributors. Recovered by branching off the bad commit, hard-resetting `main` to `origin/main`, then pushing/PR'ing/CodeRabbit-reviewing/merging normally. Future template text for "target repo readiness" pre-run steps should say explicitly: any fix needed to make the target's own test suite pass goes through a branch + PR, never a direct commit to main, regardless of how trivial the fix or how solely-owned the fork is.
